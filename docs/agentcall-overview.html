1What agentcall is

agentcall turns AI coding agents into members of a team's Slack channel. People talk to them the way they would talk to a colleague, and the agents do the work and report back in the same thread.

A company's team (engineers, support, security) hears about problems from clients: a crash, a security hole, a page that won't load. Today someone has to read the report, reproduce it, find the code, fix it and open a pull request. agentcall gives that work to agents:

  • Triage client issues, including sensitive ones like security reports.
  • Fix the code and open a pull request on GitHub.
  • Test the product in a real cloud machine with a browser, and record the repro so the team can see exactly what the client saw.
  • Report back in Slack with a summary, the PR link and a PDF report with screenshots.
  • Answer questions from the team about the product and code.

Each workspace can create several bots, each with its own name, emoji, purpose and kind of work (for example "Sentinel 🛡️" for security, "Fixer 🐛" for bugs). OpenCode is the agent that powers every bot; the landing page also presents Claude Code and Codex as agents that work alongside.

Bring your own accounts. Each user connects their own GitHub (through the agentcall GitHub App), their own Slack workspace, their own OpenCode API key (for models and inference) and their own instabox.sh API key (for the cloud machine the agent works in).

2How a task flows, end to end

Example: a support engineer writes in #eng: "@agentcall Sentinel, a client reports an XSS on the login page".

1
Slack sends the mention to the serverThe server checks Slack's signature, ignores retries of the same event, finds the workspace and picks the bot (here Sentinel, named in the message).
2
A task is queuedStored in Postgres with the prompt, bot, repository and Slack thread. The bot reacts 👀 and posts one status message, "Got it, starting shortly", which it keeps editing as it works.
3
The worker claims itOne running task per user at a time (each user has one machine). The worker decrypts the user's keys and asks GitHub for a one-hour token limited to that single repository.
4
The machine wakes upThe user's instabox machine is created the first time, or resumed if it was asleep. The agentcall runner and OpenCode are installed once and reused.
5
The runner starts, detachedThe task description goes to a file; the secrets (OpenCode key, GitHub token, callback token) go only into the process environment. The server's job for this task is now done; the machine reports back by itself.
6
OpenCode worksClones the repository, investigates, edits the code, runs tests, takes screenshots in Chromium. Progress messages update the Slack status: "Cloning…", "Working: running tests…".
7
Results are deliveredCommits as agentcall[bot], pushes a branch, opens the pull request, renders a PDF report, uploads it into the Slack thread, then posts the summary and PR link.
8
The team keeps talkingReplying in the thread with status or cancel controls the task; any other reply becomes a follow-up task for the same bot, with the earlier answer as context.

The same task can be started from the web dashboard instead of Slack; progress, events, the summary and the PR link appear there live.

3Architecture

The server is a lightweight orchestrator. It never runs AI models itself: all agent work happens on each user's own instabox machine, so the server stays small, cheap and independent of how long agents take.

SlackMentions and thread replies come in as signed events. Bots post, edit status, react and upload files.
Web app (Vercel)
Sign-up, onboarding, dashboard. Proxies /api/v1/* to the server so the login cookie is first-party.
GitHub
agentcall GitHub App: repo access, installation tokens, PRs, webhooks.
agentcall server (Railway, Bun + Hono)
  • REST API under /api/v1
  • Slack events & GitHub webhooks
  • Task queue in Postgres
  • Worker: claims tasks, launches runs
  • Watchdog: keeps runs awake, recovers lost results
  • AES-256-GCM for every stored secret
Postgres (Railway)
Users, sessions, encrypted keys, connections, bots, tasks, events, machines, runs. Migrations run at startup.
instabox machine (one per user)
Debian with git, Node, Bun, Chromium. Runs runner.js, which drives the OpenCode CLI, git, the PR and the PDF report.
OpenCode
The agent and the models. Billed to the user's OpenCode account; free models work too.
instabox API
Create, resume, exec, files, activity leases.
Slack/Web/GitHub → server → instabox machine (exec) · machine → server (/api/v1/vm/runs/:id/events, /artifacts) → Slack thread

Why this design

  • Independent server. The queue lives in Postgres, so restarts lose nothing. Slack messages, the dashboard and the API are all just ways to create tasks.
  • Agents near the code. The machine has a real browser and a full checkout, so agents can reproduce issues, not only read code.
  • Machines report back on their own. The server doesn't hold a connection open for a 40-minute run; the runner calls back, and the watchdog reads the machine's own log if a callback is lost.
  • OpenCode SDK vs binary. The server talks to OpenCode's HTTP API only to verify keys and list models. The OpenCode binary is used only where it's required: inside the VM, to run the agent (free models also only work through the binary).

5The user journey

Sign-up and login

Only name, email and password. Passwords are hashed with argon2id. Logging in sets a 30-day session cookie (httpOnly, Secure, SameSite=Lax). Signed-out visitors to the dashboard or onboarding are sent to /login and returned afterwards.

Onboarding: five steps

#StepWhat happensRequired
1GitHub"Install GitHub App" opens GitHub; the user picks repositories. GitHub returns to /callback/github, and the server proves the installation belongs to this user before saving it.Skippable
2Slack"Add to Slack" runs Slack OAuth. Back at /callback/slack, a searchable channel picker appears; the bot joins the chosen channel and says hello.Skippable
3OpenCodeThe user pastes their API key; the server checks it with OpenCode at no cost, encrypts it and shows only the last 4 characters.Yes
4instaboxThe user pastes their key; the server checks it and shows the workspace and plan (e.g. "free").Yes
5First botTemplates (Sentinel, Fixer, Scout) or a custom bot: name, emoji, purpose, kind of work, model, repositories, optional instructions.Yes

The layout has a step rail on desktop and a progress bar on mobile. Steps slide in with direction-aware animations, connected services show a drawn check mark, and errors appear inline. The final screen lists anything still missing and links straight to it.

Dashboard

  • Connections: GitHub, Slack channel, OpenCode and instabox status at a glance.
  • Hand over a task: pick a bot, describe the work, send (⌘/Ctrl + Enter).
  • Tasks: live status (queued, working, done, failed, cancelled), the event timeline, the summary, the PR link, and Cancel.
  • Bots: create, edit, pause/resume, delete.

In Slack

  • @agentcall … in the channel starts a task; naming a bot ("Fixer, …") sends it to that bot.
  • Each bot posts under its own name and emoji and keeps one status message updated, so threads stay clean.
  • Thread replies: status, cancel / stop, or anything else as a follow-up.

6Bots and how messages are routed

A bot is a configuration for the agent: who it is and what it's for. Its fields are turned into the instructions OpenCode receives.

FieldPurpose
Name, emojiHow it appears in Slack, and how people address it.
PurposeOne or two sentences: what this bot is for.
Kind of worktriagebugfixsecuritytestingreproreviewsupport
ModelAny OpenCode model on the user's account; defaults to the free big-pickle.
RepositoriesWhich repositories it works on; the first is the default.
InstructionsOptional house rules, e.g. "always add a regression test".
EnabledPaused bots don't take new work.

Routing a Slack message to a bot

  1. Named: if the message contains a bot's name, that bot gets it.
  2. Skill match: otherwise keywords are matched to kinds of work (e.g. "XSS", "CVE", "leak" → security; "crash", "broken" → bugfix; "record", "repro" → repro) and the best-matching enabled bot in that channel wins.
  3. Thread follow-ups always go to the bot already working in that thread.
  4. If a repository is mentioned (owner/name) and the bot has it, that repository is used.

7What an agent run does on the VM

The runner (apps/server/src/vm/runner.vm.js) is a single script that the server uploads to the machine once per version. Each run gets its own folder under /data/home/agentcall/runs/<runId>.

  1. Read the task from task.json (no secrets in it).
  2. Report "started", then a heartbeat every 30 seconds.
  3. Clone the repository (shallow, 50 commits) using a git credential helper that reads the GitHub token from the environment, and create the branch agentcall/<title>-<id>.
  4. Run OpenCode with the bot's model, purpose and instructions. Its JSON event stream becomes progress updates (tool steps, throttled to one every 20 s).
  5. Collect the summary the agent wrote and any screenshots or recordings it saved.
  6. Commit and push as agentcall[bot], and open the pull request through the GitHub API.
  7. Render the PDF report with headless Chromium: summary, PR link and embedded screenshots.
  8. Upload the PDF and any videos (max 25 MB each) to the server, which posts them into the Slack thread.
  9. Report "done" (or "failed" with the reason), then clean up the working copy.

Every event is also appended to events.jsonl on the machine. That file is the source of truth if a callback never reaches the server.

8Working within the instabox free plan

The free plan allows one machine (4 vCPU, 8 GiB RAM, 20 GiB disk), pauses machines after 30 idle minutes and stops a single run at 120 minutes. agentcall is built around those limits:

One machine per user, kept

Created once, named agentcall-<user>, resumed for every task. If it was deleted in instabox, a new one is created, but only if the workspace has room.

Set up once

The runner and a current OpenCode are installed on first use. Before each later run, one quick check (under a second) confirms they're current.

One task at a time

The queue never starts a second task for a user while one is running, so the single machine is never overloaded. Other users' tasks run in parallel.

Awake only while working

An activity lease keeps the machine awake during a run and is renewed every minute; it's released at the end, so the machine sleeps and stops costing resources.

Time limits

Runs are capped by TASK_TIMEOUT_MINUTES (default 45, max 110), safely under the 120-minute cap; the watchdog ends runs past their deadline.

Light on disk

Shallow clones, and each run's working copy is deleted afterwards.

9Security model

ConcernHow it's handled
Stored secretsEvery API key and Slack token is encrypted with AES-256-GCM (random IV per value, authentication tag). Each value is bound to its owner and purpose with associated data (e.g. api_key:opencode:<userId>), so a ciphertext copied to another row fails to decrypt. Only the last 4 characters are ever shown.
Passwordsargon2id. Unknown emails take the same time as wrong passwords, so accounts can't be discovered by timing. Login and sign-up are rate-limited (10 per minute per IP and email).
SessionsRandom token in an httpOnly, Secure, SameSite=Lax cookie; the database stores only its SHA-256, so a database leak doesn't leak sessions.
Cross-site requestsBrowser requests that change data must come from the agentcall web origin; others are rejected.
GitHub accessThrough the agentcall GitHub App only: the user chooses repositories. Each run gets an installation token for one repository, valid one hour. Commits and PRs come from agentcall[bot], never the user.
Claiming installationsA signed, expiring state ties the GitHub round trip to the user, and GitHub's OAuth code proves the installation is theirs, so nobody can attach someone else's installation.
Secrets on the VMThe OpenCode key, GitHub token and callback token are passed only as environment variables of the runner process, with exec history disabled; never written to disk or task files.
VM callbacksEach run has its own random bearer token; only its hash is stored. A finished run can't be revived by a late callback.
WebhooksSlack requests are verified with the signing secret (and a 5-minute window). GitHub webhooks are verified with the webhook secret using Octokit's standard verify/receive.
Slack permissionsBot scopes only; no user token, so agentcall can never act as a person.
HTTPSecurity headers on every response; errors never expose stack traces.

10Reliability

  • Durable queue. Tasks are rows in Postgres. A restart loses nothing: queued tasks wait, and runs that finished meanwhile are recovered.
  • Safe claiming. Claims use SELECT … FOR UPDATE SKIP LOCKED inside a transaction, one at a time, enforcing one running task per user.
  • Duplicate events. Slack retries the same event when it doesn't get a fast reply; each task stores Slack's event_id and duplicates are ignored. Applying the same VM event twice has no effect.
  • Lost callbacks. Every minute the watchdog renews leases for active runs. If a run hasn't been heard from in 3 minutes, or is past its deadline, it reads events.jsonl from the machine and applies the final result; if there is none past the deadline, it stops the run and marks it "ran out of time".
  • Half-started tasks. Tasks marked running for 15 minutes without a run (e.g. the server restarted mid-launch) are failed with a clear message.
  • Retries. instabox calls retry on rate limits and temporary errors, reusing an idempotency key so retried actions never happen twice.
  • Graceful shutdown. On deploy the server stops taking requests, waits for launches in progress, then closes the database.

Deleting a user deletes everything that belongs to them. Migrations live in packages/db/drizzle and are applied automatically when the server starts.
